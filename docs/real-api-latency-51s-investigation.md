## 1. 范围界定

- **调查对象**：本项目自己的网关 `https://ooioo.work/v1`（OpenAI-compatible，newapi 聚合，模型 `gpt-5.6-terra`）与**本项目的平台链路**（compose 栈：api/worker/postgres + `OpenAICompatibleProvider`）的 45–60s 延迟现象（试点 p50 23,586 / p95 45,453 / max 60,179 ms）。
- **不在范围**：顾问语境中的「方舟 doubao ep-xxx 200 并发」是**另一个接入点**，我们没有任何它的数据。本报告不对它下任何结论，但**排查方法（分位数、TTFT、并发阶梯、平台 vs 直连同并发对照）可直接套用到该接入点**。
- 顾问的「51s」与我们的数字不是同一现象：我们实测到的对应物是「试点 C=100 下 p95 45.5s / max 60.2s（60s 超时上限）」。下文所有「51s」均指「数十秒级端到端延迟」这一类现象在本网关上的成因。

## 2. 方法（可复现）

- 所有实验脚本用项目 venv 的 `httpx` 0.28.1 直连网关，请求 payload 与 `backend/app/inference/provider.py` **完全同形**（system+user、`max_tokens`、`response_format=json_object`），user 消息与 `prompt.py` 的 `build_user_message` 同构（persona_snapshot/product/question/output_schema，固定同一个画像，全实验复用）；transport `retries=0`、请求超时 60s（与 `MODEL_TIMEOUT_SECONDS=60` 一致）；**直连实验不做任何重试，失败计入该档错误率**。
- 实验窗口：2026-09-21 10:42–10:49（约 7 分钟内连续完成，时间戳来自各结果文件 mtime）——这个「窗口很短」的事实本身进入了结论（见 E3）。
- 各实验设计要点：
  - **E1**（回答顾问建议①/可能2）：C=1 顺序执行；非流式 ×3（max_tokens=256）测 e2e；流式 ×3（max_tokens=100，`stream_options.include_usage`）测 TTFT（首个 content chunk）与总时长。
  - **E2**（回答可能1）：不新增调用，用 E1/E5 的非流式样本算 `completion_tokens / duration` 得实际 tokens/s，再反推「51s 对应多少输出 token」。
  - **E3**（回答可能3）：直连（不经平台）`asyncio.gather` 同步打满 C=10/30/60/100 四档；每档记录分位数与错误码分布；档间隔 10s。
  - **E4**（回答可能4）：不新增调用，试点（平台链路 C=100）vs E3 直连同/近档对照；结合已裁定的 run 行锁上限（≈90 rows/s，TEAM-BRIEF §7.17.3）做理论核对。
  - **E5**（回答可能5）：宿主环境存在 `HTTPS_PROXY/HTTP_PROXY=http://127.0.0.1:58101`（`ALL_PROXY`/`NO_PROXY` 为空）；同 prompt C=1 各 2 次：`trust_env=True`（httpx 默认，走代理）vs `trust_env=False`（直连）。背景：平台 compose 容器内**无代理变量**，即生产链路本来就是直连。
  - **E6**（回答问题2）：试点分位数（p50/p95/max）+ E3/E3b 新数据分位数汇总；试点 attempts 原始数据已随 `compose down -v` 销毁，P90/P99 无法从旧数据补算（如实声明，见 §3.6）。

## 3. 结果（原始数据）

### 3.1 E1：C=1 单点基准 + TTFT

非流式（max_tokens=256，C=1，直连）：

| # | duration_ms | prompt_tokens | completion_tokens | e2e 有效速率 (tok/s) | finish |
|---|---|---|---|---|---|
| 1 | 39,697 | 4,367 | 215 | 5.4 | stop |
| 2 | 24,635 | 4,367 | 193 | 7.8 | stop |
| 3 | 18,507 | 5,209 | 46 | 2.5 | stop |
| 汇总 (n=3) | min 18,507 / p50 24,635 / max 39,697 / **mean 27,613** | | | | |

流式（max_tokens=100，C=1，直连）：

| # | TTFT_ms | 总时长 ms | delta chunks | completion_tokens | TTFT 后生成速率 (tok/s) |
|---|---|---|---|---|---|
| 1 | 2,159 | 3,750 | 40 | 47 | 29.5 |
| 2 | 5,413 | 6,774 | 39 | 46 | 33.8 |
| 3 | 16,713 | 19,315 | 47 | 55 | 21.1 |

**关键读数**：
- **C=1（零并发）非流式 e2e 已达 18.5–39.7s（均值 27.6s）**——数十秒级延迟**不需要并发**就能出现，这直接框定了归因方向。
- TTFT 2.2–16.7s（中位 5.4s）：首 token 之前有秒级到十几秒的纯等待（网关排队/上游预填充），非流式下这段用户什么都收不到。
- TTFT 之后流式生成速率 21–34 tok/s，**远高于**非流式 e2e 表观速率（2.5–7.8 tok/s）⇒ e2e 时间 ≈ TTFT（可变、可达 17s）+ 生成时间；非流式把两者串行一次性呈现。
- 流式 3 样本总时长（3.8–19.3s）整体低于非流式（18.5–39.7s），但输出也更短（46–55 vs 46–215 tok）且 n=3，**不构成**「流式更快」的因果结论（见 §8 未验证项）。

### 3.2 E2：输出长度归因（不新增调用）

- 实测 tokens/s（C=1 非流式 e2e 口径）：**2.5 / 5.4 / 7.8 tok/s**（3 样本）；加上 E5 的 4 个 C=1 样本：5.9 / 9.0 / 10.2 / 12.2 tok/s。合并 7 个 C=1 非流式样本：**2.5–12.2 tok/s，中位 ≈7.8**。
- 反推：**51s 在本网关对应 ≈ 128–612 输出 token（按 2.5–12 tok/s）；按中位速率 ≈ 400 token**。我们平台实际输出仅 **146–230 tokens**（≤256 上限，`finish_reason=stop` 未截断）。
- 判定（按任务书口径）：若 tokens/s 实测 ≈8–10，则 23.6s 的 p50 **不能只用输出长度解释**——实测跨了 2.5–12.2，**慢速时段（≈5 tok/s）下 230 tok 需要 ≈46s**，输出长度在慢速窗口**可以**贡献大头；但**同一 46-token 输出**在 E5#2 只花 3.77s、在 E1#3 花 18.5s（同为 C=1）⇒ **网关自身的时间波动（≈5×）大于输出长度效应**。结论：输出长度是「数十秒」的**必要放大器**（乘数），不是充分成因（见 §5）。

### 3.3 E3：直连并发阶梯（200 次调用，无重试）

| 档 | 时刻 | ok / calls | 错误分布 | 延迟（ok 样本） | wall_clock |
|---|---|---|---|---|---|
| C=10 | 10:45:58 起 | **0 / 10** | SERVER_ERROR×10（均为 httpx.TransportError，无 HTTP 状态码，**全部在 5.02–5.08s 失败**） | — | 5.1s |
| C=30 | 稍后 | **0 / 30** | SERVER_ERROR×30（同形态，5.06–5.1s） | — | 5.2s |
| C=60 | 再后 | **58 / 60** | SERVER_ERROR×2 | min 5,780 / **p50 6,586** / p90 17,448 / p95 18,735 / p99 23,309 / max 23,742，mean 8,849 | 23.8s |
| C=100 | 再后 | **0 / 100** | **RATE_LIMITED(429)×96** + SERVER_ERROR×4（网络层） | — | 9.1s |

E3b（C=10 重跑，10:48，检验时间性）：

| 档 | ok / calls | 错误 | 延迟 |
|---|---|---|---|
| C=10（重跑） | **10 / 10** | 0 | min 15,045 / **p50 16,788** / p90 19,722 / p99 19,794 / max 19,802，mean 17,194 |

**关键读数（务必一起读）**：
1. **首次实测到 429**：试点期间 0 次 429，本轮 C=100 突发 96/100 个 429 ⇒ 网关**存在突发并发/速率阈值**，且其行为随时间/上游状态显著变化（试点时点未见 429 ≠ 无限流）。
2. **阶梯非单调**：C=10/30 全灭（网络层 5s 快速失败）发生在 C=60（58/60 成功）**之前几分钟**；C=10 重跑又全部成功。四档在 ~3 分钟内先后执行，**「并发→失败」与「时间→失败」两个变量在本轮数据里无法解耦**——如实声明：阶梯曲线**不能**解读为干净的并发响应函数，只能得出「网关健康度在分钟级窗口内剧烈波动 + C=100 突发触发 429」两个可靠结论。
3. 失败形态两类：**HTTP 429**（网关显式限流，响应 ~5.1–5.3s+）与 **网络层快速失败**（无状态码、稳定 ~5.0s，疑似网关/上游在过载时重置连接——成因未查，如实标注）。

### 3.4 E4：平台链路 vs 直连同/近档对照（不新增调用）

| 口径 | 链路 | 成功率 | 延迟 |
|---|---|---|---|
| 试点 100 人（C=100，2026-09-21 凌晨） | 平台（worker + provider，含 DB 领取/finalize，`duration_ms`=claim→finalize） | **99/100 attempts 成功**（~15% 首调失败后靠重试收敛） | min 5,971 / **p50 23,586** / p95 45,453 / max 60,179 (n=99) |
| 本轮 E3（C=100，直连，无重试） | 纯 HTTP | **0/100**（96×429） | — |
| 本轮 E3（C=60，直连，无重试） | 纯 HTTP | 58/60 | **p50 6,586** / p90 17,448 / p99 23,309 |
| 本轮 E1/E5/E3b（C=1，直连） | 纯 HTTP | 13/13 | p50 ≈ 7.7s（13 样本合并：3.8–39.7s，含多个 15–40s 样本） |

- **直连 C=100 比平台 C=100 更差**（本轮直连 0% 成功 vs 平台 99% 最终成功）⇒ 平台的重试 + 暂停-恢复（§6.4）不是开销，是**必要的韧性层**。
- 理论核对（已裁定事实，TEAM-BRIEF §7.16.3/§7.17.3）：run 行锁领取路径上限 ≈ **90 rows/s**；L=23.6s 时吞吐上限 `C/L = 100/23.6 ≈ 4.2 rows/s`，**远低于** 90 ⇒ 平台链路在结构上不可能绑定在 4–24s 的量级上。实测对照与此一致：平台 p50 23.6s 与直连 C=1 的量级（18.5–39.7s）相同 ⇒ **平台开销在实测分辨率下不可见**。
- 口径差异须注明：试点 `duration_ms` 含 claim→finalize（含 DB 写入），直连为纯 HTTP 往返；该差异只会让平台数字**偏高**，而平台 p50 仍与直连 C=1 同量级，不影响「平台非瓶颈」的方向。

## 4. 对顾问 6 个问题的逐条回答（每条给实测数字）

1. **时间花在哪一层？** —— 在**网关/上游模型服务层**，不在应用与平台层。证据：零并发直连单请求 e2e 就有 18.5–39.7s（E1），而平台 p50 23.6s 与之同量级（E4）；平台领取路径上限 ≈90 rows/s，比 L=23.6s 下的需求吞吐 4.2 rows/s 高一个数量级以上（§7.17.3 已裁定不改代码，本调查也不改）。
2. **P50–P99 分布如何？** —— 平台链路（试点，n=99）：min 5,971 / p50 23,586 / p95 45,453 / max 60,179 ms；**P90/P99 因旧数据销毁无法补算**（如实声明）。本轮直连新数据：C=60 p50 6,586 / p90 17,448 / p99 23,309；C=10 p50 16,788 / p90 19,722 / p99 19,794（§3.6 汇总表）。
3. **模型与接入点是什么？** —— `gpt-5.6-terra` @ `https://ooioo.work/v1`（newapi 聚合网关，OpenAI-compatible，非流式，`response_format=json_object`，key 走 `SURVEY_MODEL_API_KEY`）。顾问提到的「方舟 doubao ep-xxx」**不在本次调查范围**（无该接入点任何数据）。
4. **max_tokens 与 stream 的影响？** —— `max_tokens=256` 全程**未发生截断**（实测输出 44–230 tokens，`finish_reason=stop`，含试点 146–230）⇒ 上限不是延迟原因，实际输出长度才是。流式实测：**TTFT 2.2–16.7s**（C=1），TTFT 后生成 21–34 tok/s；流式**不减少总生成时间**，但把「首响应」从全量等待（18.5–39.7s）提前到 2.2–16.7s（n=3，方向性结论）。
5. **错误率与降级行为？** —— 同一网关两轮差异巨大：试点（凌晨，C=100）首调失败 ~15%（SERVER_ERROR×9 + TIMEOUT×6 / 100 首调），**0 次 429**；本轮（上午，直连）C=100 突发 **96/100 个 429** + 4 个网络层快速失败（~5s），而 C=60 档仅 2/60 失败 ⇒ 网关存在**突发并发阈值**（位于 60–100 之间某处，本轮未精确定位），且其健康度/限流策略**随时间变化**（试点 0 个 429 vs 本轮 96 个；C=10 先全灭后 10/10 成功）。TIMEOUT 均为平台 60s 上限截断，非网关显式错误。
6. **平台链路 vs 直连是否同速？** —— 同/近并发对照（§3.4）：平台 C=100 p50 23,586 ms vs 直连 C=1 量级相同、直连 C=100 本轮反而 0% 成功。**未观察到平台引入的额外可测延迟**；平台的重试与暂停-恢复机制在突发失败下把最终成功率从 0%（直连无重试）提升到 99%（99/100 成员成功）。

## 5. 顾问 5 类假设逐条判定

| # | 假设 | 判定 | 依据（原始数据） |
|---|---|---|---|
| 可能1 | 输出长度（生成 token 太多） | **部分成立（放大器，非充分成因）** | 平台输出仅 146–230 tok；按实测 C=1 非流式 2.5–12.2 tok/s，230 tok 需 19–92s（中位速率 ≈30s）⇒ 长度×慢速构成 p50 23.6s 的主体；但同一 46 tok 的输出耗时 3.77s（E5#2）与 18.5s（E1#3）差 5× ⇒ 网关波动 > 长度效应；且我们场景无「几千 token 长输出」，顾问语境的长输出归因**不适用于**我们网关的量级。 |
| 可能2 | 非流式（等待全量生成） | **部分成立** | 非流式 e2e = TTFT（2.2–16.7s，中位 5.4s）+ 全量生成一次性呈现；TTFT 段是纯等待。但流式只是改善首响应，**不缩短总生成时间**；把延迟从「数十秒」降一个量级不能靠流式单独实现。 |
| 可能3 | 限流降级 | **成立（且比顾问猜的更活跃）** | C=100 直连突发 96/100 个 429（首次实测到 429，试点为 0）；C=60 仅 2/60 失败 ⇒ 存在突发并发阈值（60–100 之间）；另有分钟级健康度波动（C=10 先 0/10 后 10/10）。网关行为随时间变化是本轮最大意外。 |
| 可能4 | 本地平台瓶颈 | **不成立** | ① 理论：领取路径上限 ≈90 rows/s ≫ C/L≈4.2 rows/s（L=23.6s），平台结构上不绑定；② 实测：平台 C=100 p50 23,586 ms 与直连 C=1（18.5–39.7s）同量级；直连 C=100 本轮 0% 成功而平台同规模 99% 最终成功。平台开销在实测分辨率下不可见。 |
| 可能5 | 本机资源/代理 | **不成立（代理维度已实测排除；本机资源未直接测量）** | 代理 vs 直连 C=1 对照：均值 4.9s vs 6.0s，差异不显著且方向相反（§3.5）；compose 容器内本无代理变量。本机 CPU/内存因沙箱禁用 `ps` **未直接测量**，但 13/13 的 C=1 调用无客户端侧异常，无任何数据指向本机资源瓶颈。 |

## 6. 对「51s（数十秒级端到端）」的最终归因（以实测为准）

**主因 = 网关/上游服务侧的每请求服务时间长：TTFT（C=1 即达 2.2–16.7s）+ 全量生成（输出 146–230 token × 有效速率 2.5–12 tok/s），使零并发直连单请求已达 18.5–39.7s；并发突发（C=100）再叠加网关突发限流（96/100 个 429）与分钟级健康度波动，把 p95 推到 45.5s、尾部顶到 60s 超时上限——平台链路与代理/本机资源实测不构成可观测的额外延迟。**

## 7. 建议（按证据强度排序）

1. **保留并信赖平台现有的重试 + 暂停-恢复机制**（零成本）：E4 实证直连无重试在 C=100 突发下 0% 成功，而平台收敛到 99%。
2. **并发阶梯爬升**（试点已建议，本轮强化）：从 30→60→100 爬升，避开突发 429 阈值；C=60 档 58/60 成功且 p50 仅 6.6s，是本轮实测「最划算」的并发点。
3. **流式化（改善感知与可控性，非提速）**：TTFT 2.2–16.7s vs 全量 18.5–39.7s；流式还使「过慢请求」可在生成中途被取消，减少 60s 超时浪费的槽位占用。属中等平台改动，建议作裁决项。
4. **压短输出**（低成本、按比例生效）：`reason` 字段限长已在（100 字符）；若把输出压到 ~80–120 token，按中位速率 p50 可近似减半。与 `max_tokens` 无关（256 从未触顶）。
5. **平台代码优化（run 行锁等）不值得做**：已裁定不改代码（§7.17.3），本调查再次确认非绑定（90 rows/s ≫ 4.2 rows/s 需求）。
6. **若需个位数秒级延迟 ⇒ 换接入点/网关**：本网关零并发也要 18.5–39.7s，这不是调客户端参数能解决的；1,000 人阶段前建议向网关方核实限流策略与容量（429 行为随时间变化，试点 0 → 本轮 96）。

## 8. 未验证 / 假设项（显式声明）

- **「51s」原文语境（方舟 doubao ep-xxx，200 并发）无我们任何数据**：本报告仅回答「我们网关 + 平台链路」的同类现象；方法可迁移，数字不可迁移。
- 试点 **P90/P99 与均值无法补算**（attempts 数据已随 `compose down -v` 销毁，如实声明）。
- **E3 阶梯的时间混淆**：四档在 ~3 分钟内先后执行，C=10/30 全灭与 C=60 成功的顺序（非单调）无法解耦「并发效应」与「时间效应」；突发并发阈值只能定位在 60–100 之间，未精确测量。
